# ニコニコ通信・応答の診断記録

通信の成否と、取得した情報を使えるかどうかを別の境界として記録します。監視のための追加通信・再試行・ポップアップは行いません。通信先の仕様が変わったと断定せず、「応答の形式を読み取れない」と記録します。

## 今回接続した経路

| 経路 | 記録する境界 | 実装 |
| --- | --- | --- |
| 共通fetch | 通信例外、時間切れ、HTTPエラー、後続の正常応答 | `netUtil` → `RequestDiagnostics` |
| 別オリジン経由fetch | ゲート呼び出しの成否。ローカルの所有判定は送信前に取り除く | `netUtil.fetch` → `NicoVideoApi` |
| JSONP | 対応するニコニコAPIの呼び出し失敗・次回成功 | `netUtil.jsonp` |
| 動画情報 | 応答を読み取る処理、既存の再試行、削除・権限・有料等の区別 | `VideoInfoLoader` |
| コメント取得・取得キー | JSON/API状態・コメント形式・キー形式の確認、既存の再試行後の成功 | `ThreadLoader`、既存 `CommentReadAdapter` |
| 再生セッション | 作成・接続の拒否、状態取得で分かる異常終了 | `VideoSessionWorker` のメインスレッド側 |

共通fetchではURLをそのまま保存せず、動画情報・コメント・検索・マイリスト・プレイリスト・いいね・タグ・場面情報・その他のニコニコAPIという固定の識別名に変換します。対象外ホストの通信は記録しません。`netUtil`を使う他のAPIも通信段階の監視対象ですが、全APIの応答形式を新たに検証するものではありません。

共通通信の固定分類にはタグ候補・ニコニ広告・広告装飾・支援者・ギフト・大百科・関連動画・投稿者を追加しました。APIごとの応答確認は上表の境界だけです。ランキング、RSS、親子作品、動画情報の追加補完、コメント投稿などの専用応答検証は未接続で、netUtilを経由する部分だけ共通通信の監視対象です。正常応答の取得件数や本文は履歴へ複製しません。

## 接続方式

```text
共通通信 / APIの応答確認 / Workerの呼び出し窓口
  → RequestDiagnostics（安全な分類、現在の処理か判定、復旧追跡）
  → initializerで設定したsink
  → NotificationJournal.recordDiagnostic（同じ行を更新）
  → NotificationJournalPolicy → NotificationJournalStore
```

`RequestDiagnostics`はUIやDBに依存しません。メインUserScriptの初期化で通知履歴へ接続します。補助UserScriptに同じライブラリが含まれていても、それだけでメイン画面の履歴へ転送されるわけではありません。

繰り返し発生した同じ機能・対象・段階の失敗は、同じ履歴行の発生回数と直近の診断情報を更新します。成功だけの履歴は作りません。復旧すると同じ行を「復旧済み」に変え、最後の失敗理由・HTTP状態・回数を残します。履歴消去はグループ情報も消すため、過去の復旧通知だけで削除済み行を復活させません。

HTTP 200とデータの正常性は別です。履歴の見出しも「通信」「応答の確認」「処理」を区別します。同じ操作で通信段階と上位段階の両方が失敗した場合は、段階ごとの行になります。操作全体を一つのトレースへ統合する相関IDは、この段階では導入していません。

## 安全性と上限

- 保存するのは固定の機能名・段階・結果・失敗分類、許可したエラーコード、数値のHTTP状態・所要時間・発生回数です。
- 生URL・検索語・本文・Cookie・ヘッダー・取得キー・応答全体・例外メッセージは保存しません。対象識別用のダイジェストもメモリ内のグループキーだけで、履歴には保存しません。
- 明示的な中断と、所有者が無効になった古い処理は除外します。動画情報取得では動画切替世代も通信まで渡します。`diagnosticActive`はローカル専用で、fetchやゲートの送信情報に残しません。
- 同じ対象の新しい処理が始まると、古い結果で状態を上書きしません。異なる対象の実行中処理は別に追跡し、完了時に解放します。
- 未復旧の追跡は直近100グループ・10分です。それを超えたものは後日の成功で復旧表示に更新されない場合があります。正常通信はこの枠を消費しません。保存履歴は既存の上限2,000件のままです。
- 診断先の例外は呼び出し元へ伝えません。通信結果・エラーの同一性、キャンセル、再試行の既存動作を維持します。

## 別経路として残る場所

| 経路 | 現状・次の接続点 |
| --- | --- |
| HLSの動画断片・マニフェスト | 別UserScriptとhls.jsの通信。`HlsEntry`の既存エラー分類を安全なイベントへ変換する必要がある |
| コメント増量 | `packages/comment-history/src/transport.mjs`に独立したタイムアウト・エラー分類がある。パッケージの境界から報告するのが適切 |
| Worker内の直接fetch・場面画像/CDN | 今回はセッション窓口の結果を記録。画像単位・ハートビートHTTP応答そのものは未接続 |
| 補助UserScriptの独立実行 | メインの履歴への転送は別の接続契約が必要。Window間へ生の例外やURLを送らない |
| 各APIの個別形式検査 | 動画情報・コメントを優先。他のAPIは既存の検証境界に順次接続する |

これらを理由にブラウザ全体のfetchを置き換えたり、すべてのエラーを一括で捕捉したりはしません。新しいAPIには、通信の共通経路と、そのAPIの応答を検証する位置の両方を確認して接続します。

実機での確認対象は、通常再生・動画切替・コメント取得が従来どおり動くこと、通知履歴に発生回数が表示されること、履歴消去後に古い行が復活しないことです。エラー発生のために連続リクエストや投稿を行う必要はありません。

## Task994: 履歴詳細と広告の対象なし

履歴の `version` / `build` は記録時の本体から取得します。`firstOccurredAt` / `lastOccurredAt` は失敗発生時刻、`recoveredAt` は後続の成功を確認した時刻です。復旧で最終失敗時刻を上書きしません。旧記録の欠落情報を現在の版や時刻で補完せず、画面で未記録と表示します。DBの構造・保存上限は維持します。

`UaaLoader` のthanks取得は、同じ応答を通信と応答確認で二重記録しないよう取得境界が診断を所有します。404は全て履歴に残します。2026-11-10の匿名GETでHTTP404/meta404、RESOURCE_NOT_FOUND、スポンサー不在という応答を確認しましたが、それを理由に正常として除外しません。HTTP状態・許可済みエラーコード・件数だけを記録し、応答本文は保存しません。HTML/不正JSONの場合もHTTP状態とRESPONSE_SCHEMAを残します。他のAPIの404や診断は維持します。

表示では「対象なし・要確認」とし、広告なし・対象外・API変更をこの応答だけで区別できないことを説明します。新たな自動再試行・追加通信は行いません。
